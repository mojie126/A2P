### 果办免费套餐机制结论（上游实测，2026-11-06 至 11-08）

- `client-subscription` 开通请求会被上游受理，但该账号的 `subscribe_status` 始终停留在 `UNSUBSCRIBED`，签到与领取持续 403 `OfficeAce.11020604` 未订购套餐
- 旧版实现的 pending 标记只有官方返回 `SUBSCRIBED` 才清除，且期间不重试，形成「一直结果待确认」死锁；`adbb467` 之后十分钟自动回落并允许重试
- 真正的免费体验套餐开通链路在华为云 CodeArts 控制台（码道域），与果办 `client-subscription` 解耦，自动化下单被 CloudWAF 拦截——网关侧无法真正开通，需在官方客户端人工操作（详见 11-06 文档第三节）

## 供应商上游基线与排查结论（2026-11-05 至 11-08 实测）

范围：ZCode、AutoClaw、OfficeAce（果办）三家在 2026-11-05 至 2026-11-06 的故障排查结论、上游接口基线实测与本地代码改动，另附 trae 工具声明警告的归因与 Qoder 国际版签到的环境指纹结论。

### 一、ZCode

#### 上游基线实测（2026-11-06 凌晨，接口域名 https://zcode.z.ai）

- 套餐探测接口 `/api/v1/zcode-plan/billing/preview`：匿名请求（无 Authorization）返回 HTTP 401 空响应体，带 WAF Cookie 二次握手仍 401，判定上游已关闭匿名访问；携带账号 JWT 返回 HTTP 200 且业务码为 0，四个账号（国内版与国际版）登录态全部有效
- 营销接口 `/api/v1/marketing/touch` 携带 JWT 返回 200，`deliveries` 为空
- 客户端版本门槛（2026-11-06 探测、2026-11-10 复测修正）：`app_version` 3.18.0 至 3.21.0 探测到的 `plans` 均为空，当时推测 3.22.0 起才可能拿到套餐；2026-11-10 用正确凭证（账号 `jwt` 字段，此前误用 `accessToken` 全部 401）复测证实：真实客户端版本 **3.17.2**（官方 changelog 最新，https://zcode.z.ai/cn/changelog）与 3.18.0 的响应完全一致（HTTP 200、code=0、空列表），且现网账本证明插件在 11-05 至 11-09 期间天天领到套餐——空列表的原因是**当期没有可领取活动**，与版本号无关；插件默认值随即从虚构的 3.18.0 对齐到真实客户端 3.17.2
- 当日赠送套餐北京时间 19:00 起可领，活动期上游每天下发 `zcode-v3-start-plan-<日期>` 形态的套餐
- 领取动作上游强制人机验证（阿里云验证码，官方 SDK 求解）：19:01 定时领取四个账号全部失败，失败原文为「需要人工验证：没有可用的验证界面」；实测手动领取无滑块弹窗，验证基本无感通过

#### 故障定位

- 「ZCode 匿名目录未完成：登录态已失效，无法探测套餐」：匿名目录探测本就不携带凭证，401 是上游关闭匿名访问所致，报错文案误导
- 自动领取失败的原因：面板页在浏览器形态（`platform === 'web'`）且 `document.visibilityState` 非 visible 时主动把验证客户端标记为不就绪（A2API 仓库 `ui/zcode-claim-verification.js` 的 `canVerify`），且浏览器对后台标签页的定时器节流使 5 秒心跳撑不住插件侧 40 秒客户端有效期，调度端因此报「没有可用的验证界面」
- 本地改动：A2API 仓库 `desktop-tauri/ui/zcode-claim-verification.js` 取消浏览器形态的前台可见性门槛，并增加 Worker 心跳通道，后台标签页也能按 5 秒节奏接验证任务

### 二、AutoClaw

#### 上游基线

- 刷新链路：`POST /userapi/v1/refresh`（签名头 `X-Auth-Sign = MD5(appId&ts&appKey)`），业务码 400002 时降级 `POST /userapi/v1/agent-refresh` 再试
- 访问令牌为 24 小时有效期；插件每小时无条件强制刷新一次，用于温着会被服务端轮换的 refresh_token
- 回写口径：插件 `persist_refresh` 同时写两套键（`token` / `tokenExpiresAt` 与 `accessToken` / `expiresAt`），写前做比较再写
- 实测两个账号库存的 `token` 与 `refreshToken` 均带 `Bearer ` 前缀（总长 382 / 383，含 7 字符前缀）

#### 故障定位与本地改动

- 现象：凭证刷新报「账号……的凭证刷新未产生变化（适配器报成功但凭据未更新）」（A2API 仓库 `credential_maintenance.rs` 的 `refresh_checked` 指纹核对）
- 根因：`persist_refresh` 回写前用「剥过前缀的凭证快照」与「库里带前缀的原值」比较，恒不相等，被误判为「凭证已被别处换过」，于是跳过回写并把旧令牌按成功返回；主仓指纹未推进即报错。刷新本身可能已在上游成功，但结果被整体丢弃
- 修复：比较与兜底读取两侧统一先剥前缀（`crates/providers/src/providers/autoclaw/mod.rs`）
- 残余观察点：若上游在令牌有效期内始终原样返回旧值（不轮换），每小时强刷仍会在主仓指纹核对处报「未产生变化」，需在令牌到期窗口实测确认上游是否真轮换

### 三、OfficeAce（果办）

#### 上游基线实测（2026-11-06）

- 两层凭据：网关 Basic（转发用，不过期）与控制面临时 AK/SK + securityToken（约 2 小时有效期，DPoP + refresh_token 续期链路实测正常，到期前 30 分钟插件自动续期）

#### 微信小程序「果办」接口面还原（2026-11-06，解包 wxapkg 实证）

- 代码包：微信 4.x PC 端小程序包落在 `%APPDATA%\Tencent\xwechat\radium\users\<用户哈希>\applet\packages\<小程序 appid>\`，`V1MMWX` 加密（AES-256-CBC，密钥 = PBKDF2-HMAC-SHA1(appid, "saltiest"，1000 轮，32 字节)，IV = `"the iv: 16 bytes"`，密文段 1023 字节 + 1 字节标记 + 余量按 appid 倒数第二字符异或；容器头 `0xBE` + 8 字节索引长 + 4 字节正文长 + `0xED` + 4 字节文件数）。三个包全部解开，密钥只由 appid 派生，不涉及用户隐私
- 业务主机：正式 `https://officeace.chat.huaweicloud-agentarts.com`，灰度 `officeace-gray.chat.huaweicloud-agentarts.com`；业务前缀 `/v1/appapi`
- 登录链路（无鉴权面 `/v1/wx-login/` 与 `/v1/appapi/auth/callback`）：`wx.login()` 取 code → `POST /v1/wx-login/auth/login` 返回 `auth_token`；`POST /v1/wx-login/huawei-login-url`（手机号短信）返回 `authorize_url` 与 `session_id` 进华为云 OAuth；`POST /v1/appapi/auth/callback` 完成回调落 `account_profile.credential`
- 业务鉴权头：`Authorization: OfficeAceToken <credential>`（临时态为 `Bearer <auth_token>`）；另有 `X-Application-Id`、`X-Chat-User-Id`、`x-apig-appcode`（当前构建为空）
- 签到动作：`POST /v1/appapi/subscription/bonus/claim`，查询 `GET /v1/appapi/subscription`、`GET /v1/appapi/subscription/usage/detail`——与网关侧是同一业务动作的不同接入面（不同鉴权方案），小程序 UI 同样把 `UNSUBSCRIBED` 归入领取失败态

- 结论：小程序「签到成功」与网关签到是同一业务动作；接入价值有限：网关已有同一动作的 IAM 签名链路，差异只在鉴权面与主机

### 四、trae 工具声明警告归因

警告原文：`剔除原生（服务端执行）工具声明 1 条：web_search（本上游只承载 type:"function" 的函数工具）；provider=trae`

- 出处：A2API 仓库 `core/upstream/payload.rs` 出站处理的第 ④ 层「原生（服务端执行）工具声明闸门」，明细逻辑在 `core/protocol/native_tool.rs`
- 触发条件：客户端请求的工具声明里带了协议私有的服务端执行工具（Responses 协议的 `{"type":"web_search"}` 或 Anthropic 协议的 `web_search_20250305` 这类，常见于客户端开启了自带联网搜索），而 trae 上游只承载 `type:"function"` 的函数工具，上游对原生工具的处理是静默剔除（同类声明发给 CatPaw 则是整轮 400）
- 处置行为：网关出站前统一剔除并留痕，属于按设计的降级，不是错误；被剔除的只有服务端搜索声明，客户端声明的函数工具不受影响。若确认某家上游支持某类原生工具，可在该闸门按家按类型开白

### 五、Qoder 国际版无法签到（2026-11-06 实测结论）

- 现象：Docker 网关（NAS）上 `qoder-intl` 每日签到返回「该账号今天没有可领取的每日积分活动（上游未下发，与本机环境无关）」，中国版正常
- 接口对照（真实账号令牌，`GET https://openapi.qoder.sh/sash/api/v1/me/campaigns?forceRefresh=true`）：不带风控头只有 `VIEW_DETAILS` 促销活动；带 Docker 内 UMID 组件生成的头同样无积分活动；带本机桌面客户端生成的头立刻出现 `CLAIM_BENEFIT CLAIMABLE` 活动
- 差异点：两份组件自报的环境指纹不同（`{"isVm":true,"brand":"Docker","percentage":90}` 与 `{"isVm":true,"brand":"Hyper-V","percentage":77}`）；上游设备风控把 Docker 环境判为高风险，不向该设备下发每日积分活动
- 结论：不是接口路径、鉴权或凭证问题，而是**运行环境指纹**问题

## dev-build 流程基线

- 触发：仅 `workflow_dispatch` 手动触发，无需输入，版本号取 `pack.json` 的 `version`
